## 二、安全演练

> **先说清一个口径差异。** 本次先用了一种**差异范围**的安全扫描（只认"本次改动引入、且可证实可利用"的问题），
> 其结论是：**当前未提交变更（抖音公开接口同步、直链域名判断修复、播放串台修复）未引入可证实利用的安全问题**。
> 那个口径会主动排除"既有代码 + 配置类加固缺失"，所以你下面看到的 A1/B1/B2 等**都是本次改动之前就存在的**——
> 它们在你要求的"演练范围"内（用户与开发者风险），但在"差异范围"内不算。两者不要混为一谈。

### A. 客户端自身

#### A1【中】任意应用可让本应用载入并渲染任意网页（界面伪装 / 钓鱼面）

**证据链**

1. `MainActivity` 导出且注册了 `ACTION_SEND`：`AndroidManifest.xml:[29,49]`
2. 收到分享文本后**自动解析**，无需用户确认：`MainActivity.kt:[45,51]`
3. 平台识别用的是**子串正则**，未锚定主机名边界：`ytdlp_engine.py` 的 `PLATFORM_RULES`
4. 于是这些构造都能被判为「抖音」（实测输出）：

```
抖音  <- https://attacker.example.com/x?u=//douyin.com/
抖音  <- https://attacker.example.com/?next=//douyin.com/video/1
抖音  <- https://douyin.com.attacker.example.com/video/1
抖音  <- https://attacker.example.com/redirect?to=https://www.douyin.com/
其他  <- https://attacker.example.com/video/1        （不带上述特征时不误判）
```

5. 这些 URL 取不到作品 ID，于是**降级到 WebView 并加载这个 URL**。真机日志：

```
[douyin] 接口方案失败，降级到浏览器模式：RuntimeError: 没能从链接里识别出作品编号
ActivityTaskManager: Displayed com.ytdlp.android/.DouyinActivity
```

6. **视觉证据**：用 `https://example.com/x?u=//douyin.com/` 触发后截图，可见 example.com 的页面渲染在
   **应用自己的窗口内**，上方针着应用自己的文案「正在用浏览器模式解析抖音…如果页面提示登录，登录后再等几秒即可」。

**复现步骤**

```bash
adb shell am force-stop com.ytdlp.android
adb shell am start -a android.intent.action.SEND -t text/plain \
  --es android.intent.extra.TEXT "https://example.com/x?u=//douyin.com/" \
  -n com.ytdlp.android/.MainActivity
# 观察：应用自行打开「抖音浏览器模式解析」页并渲染 example.com
```

**影响面**

- 同机任一应用（无需任何权限，因为接收方 exported）即可让本应用**前置到前台**并展示它指定的页面。
- 页面被应用自己的 UI 文案包裹，用户容易误认为这是应用的一部分 → **钓鱼 / 界面伪装**。
- 组合面：攻击者还可借此让本应用向其服务器发起请求（确认已安装、暴露 IP）。

**边界（如实说明）**

- 未能证实可借此读取用户数据：WebView 无 `addJavascriptInterface`，Cookie 按域隔离，应用未开启文件访问。
- 属于"界面与信任边界"问题，不是数据窃取。

**规避方向（待确认）**：主机名精确匹配（锚定 `://` 与域名结尾）、分享来的链接先经用户确认再解析、WebView 仅允许白名单域。

#### A2【低】engine 自检页可被任意应用拉起，并导出设置与完整历史

**证据**：`AndroidManifest.xml:[63,66]` 声明 `exported="true"` 且无权限保护；`ProbeActivity.kt:[152,157]`
启动即自动跑 4 条探针；`ProbeActivity.kt:[176,187]` 把输出同时写屏幕与 `Log.i(TAG="probe")`。

真机复现（外部拉起后 logcat 实际内容）：

```
probe: {"output_dir": "/storage/emulated/0/Download", ..., "cookies_file": "", "cookies_present": false}
probe: [{"id": "7693059298562490225", "platform": "抖音", "title": "#精致jiojio ...",
        "source_url": "https://v.douyin.com/UtBkqa1ZjkQ/",
        "resolved_url": "https://v5-se-ex-mc-default.365yg.com/...&x-signature=..."}]
```

**影响面**

- 设置项与**整份历史记录**（标题、原始链接、**带签名的直链**）进入 logcat 与屏幕。
- 每次被拉起都会额外写入 3 条历史（`parse_url` 会 upsert）→ 本地数据被污染。
- 屏幕内容会出现在**任务切换缩略图**中。

**边界（如实说明）**：自 Android 4.1 起普通应用无法读他应用 logcat，因此**未能证实**可被同机应用直接窃取；
真实暴露面是「有 adb 的人 / 屏幕可见 / 缩略图」。故定级为低。

**规避方向**：改 `exported="false"`（代价：adb 也起不来，需另设 debug-only 变体）、或加签名级权限、或去掉「读取历史」探针。

#### A3【低】全局允许明文流量

**证据**：`AndroidManifest.xml:27` `android:usesCleartextTraffic="true"`，且未提供 `networkSecurityConfig`。

**背景**：这是为了让 B站 的 `http://` 封面图能显示（README 有记录）。但该开关是**应用级**的，
影响面覆盖所有平台的所有请求与下载，而不只是封面图。

**影响面**：任何 http 资源可被同网段中间人篡改；与「下载内容完整性」相关。

**规避方向**：改用 `networkSecurityConfig`，只对封面图所在域放行明文，其余保持默认（禁止）。

### B. 数据与隐私

#### B1【中】「清除 Cookie」只清路径，不删文件 → 凭据残留

**证据**

- 设置页的清除按钮：`SettingsScreen.kt:169` → `vm.setCookiesFile("")`
- 落到引擎：`ytdlp_engine.py:[637,641]` **只把路径置空并保存设置**，没有任何删除文件的动作
- 全仓 grep `deleteFile` / `File.delete` **无命中**
- 而导入时是真写盘了：`SettingsScreen.kt:55` `val dest = File(context.filesDir, "cookies.txt")`

**影响面**：`cookies.txt` 是 Netscape 格式，含各平台登录凭据。用户点「清除」后文件仍在应用私有目录里，
后续带 Cookie 的请求（如 TikTok/X）仍可能读不到（因为路径已清）——但**凭据本身没有被销毁**。
用户以为已清除，实际只是"不再引用"。

**规避方向**：清除时同时删除 `filesDir/cookies.txt`。

---

#### B2【中】WebView 登录态无法在应用内清除

**证据**：全仓 grep `removeAllCookies` / `WebStorage` / `clearCache` **均无命中**。
而 WebView 的 Cookie 是会被读取和长期保留的：`DouyinActivity.kt:[143,146]`。

**影响面**：用户在「抖音浏览器模式」里登录后（扫码/账密），登录态落在应用的 WebView Cookie 库中，
应用内**没有任何入口**可以登出或清除，设置页那句「清除 Cookie 文件」清的也只是那个 txt 文件。

**规避方向**：设置页增加「清除浏览器登录态」并调用 `CookieManager.removeAllCookies` + `WebStorage.deleteAllData`。

---

#### B3 数据落点（正向）

| 数据 | 位置 | 说明 |
|---|---|---|
| `cookies.txt` | `context.filesDir`（应用私有） | 非公共目录，其他应用不可读 ✓ |
| 历史库 / 设置 | 应用私有目录（`filesDir`） | ✓ |
| 抖音登录态 | 应用 WebView Cookie 库 | 私有，但**不可清除**（见 B2） |
| 下载产物 | `/storage/emulated/0/Download` | 公共目录，实测权限 `-rw-rw---- u0_a0 media_rw` |

> 产物落在公共下载目录是产品设计（用户要能用文件管理器找到），但意味着同 `media_rw` 组可读，
> 用户应知情。未见应用内对此有说明。

### F1【中】断网时给出错误归因

**现象**：开启飞行模式后解析 B站，界面提示：

```
解析失败
该站点可能改版了，当前内置的解析引擎还处理不了。
可以先试试其他方式打开原视频，或等应用更新。
原始报错：ERROR: [BiliBili] 1dcLE6EEce: Unable to download webpage:
  [SSL: UNEXPECTED_EOF_WHILE_READING] EOF occurred in violation of protocol (_ssl.c:1010)
```

**根因**：错误翻译表里没有能命中这条报错的规则。

- `ytdlp_engine.py:[204,213]` 有 `timed out`、`Network is unreachable` 两条网络类规则

## 三·补 用户自测发现、本轮已修的两项（F3 / F4）

### F3【中】先下载过、之后重新解析同一条视频，仍提示"需下载后才能播放"

**现象**（用户反馈）：解析某视频 → 下载 → 之后**再解析同一条**，播放区依旧说"该站点是音视频分轨流，需下载后才能播放"。

**根因**：解析结果里**不带** `local_path`。

- 产物路径是下载完成后由我们自己记进历史库的（`set_local_path`），而解析结果来自 yt-dlp 的 `info` —— 两者本就不在一个来源里。
- `Engine._to_record` 生成的记录里没有 `local_path` 字段；Kotlin 侧 `Video.fromParseResult` 也没有读它。
- 于是哪怕历史库里明明白白存着路径（`upsert` 的 `ON CONFLICT DO UPDATE` **不会**清掉 `local_path`，这点已核实），界面也无从知道文件已经存在。
- 此前的"刚下完能播"是靠 [`播放串台修复.md`](./播放串台修复.md) 里那条补丁兜着的，而那条补丁依赖**内存里的下载状态**，冷启动即失效。

**改动**（两端同步）：

| 文件 | 改动 |
|---|---|
| `android/.../ytdlp_engine.py` | 新增 `_with_local_path()`，在 3 处解析出口（`parse_url` / 抖音接口 / `save_douyin`）把历史库里的 `local_path` 补进解析结果 |
| `windows/engine.py` | 同构实现，同样补在 3 处解析出口（保持两端一致） |
| `Engine.kt` | `Video.fromParseResult` 增加读取 `local_path` |

匹配规则：**id 优先、`source_url` 兜底**；并且**会校验文件是否还在磁盘上**，已被用户删掉就忽略，避免指向不存在的路径。

**验证**

1. 单测（两端各 4 个用例，同一份期望值）：

```
[OK] 命中 id 且文件在          安卓/Win 均补上
[OK] 命中 id 但文件已删        两端均为 None（不指向失效路径）
[OK] id 对不上、source_url 兜底 两端均补上
[OK] 都没有记录                两端均不添加该字段
```

2. 真机（冷启动后解析一条 **9 月 26 日就已下载**的 B站 视频）：

```
播放按钮存在（=可直接播本地文件）: True
仍提示需下载才能播放: False
```

冷启动意味着内存里的下载状态是空的 —— 所以这个"可播放"只可能来自历史库里的路径，即本次修复生效。

### F4【中】下载的视频不进系统相册/图库

**现象**（用户反馈）：授权"所有文件访问"之后，下载的视频在相册里依然看不到。

**取证（这台设备上的实测数据）**：同一个应用、同一个目录，**有的进了媒体库、有的没进**。

| 文件（都在 `/storage/emulated/0/Download`） | 在 MediaStore 里？ |
|---|---|
| `#ootd穿搭女生 #控腿穿搭 [7692388358463153265].mp4` | ✅ 在 |
| `大型纪录片…[BV1ckhW6DErb].mp4` | ✅ 在 |
| `#精致jiojio #日常穿搭分享 #裸色美甲 [7693059298562490225].mp4` | ❌ **不在**（磁盘上确实存在） |

这个"时有时无"正是根因的表现：**应用从不主动通知媒体扫描器**，文件能不能被收录取决于是否有别的事件（重启、挂载、别的应用扫描）碰巧触发了一次扫描。

**根因**：yt-dlp 是用普通文件 API 直接写盘的，系统并不知道多了一个媒体文件 —— Android 的 `MediaStore` **不会**自动收录（即使已授予 `MANAGE_EXTERNAL_STORAGE`）。

**改动**：`AppViewModel` 在轮询到"下载完成"的那一刻调用一次
`MediaScannerConnection.scanFile(ctx, arrayOf(path), null, null)`。
`scanFile` 是异步的、不阻塞；失败也只是不收录，不影响下载本身。

**验证**：装新包后下载一条 11 MB 的 B站 视频，**下载完成后立刻**查媒体库：

```
磁盘: -rw-rw---- 11537810 2026-10-06 12:33 你的摇杆是怎么坏玩的？… [BV1dcLE6EEce].mp4
媒体库: Row: 6026 _data=/storage/emulated/0/Download/你的摇杆是怎么坏玩的？… [BV1dcLE6EEce].mp4
```

已收录。

和可点的下载按钮，用户会把**别人的视频**当成自己的内容下走，全程没有任何提示。

**判定依据（为什么能确定是错内容）**：

1. 多条**不同链接**返回**完全相同**的标题/作者/时长（5~8 条共用同一条），这在"解析正确"时不可能发生；
2. 你标注的内容与返回内容完全无关（例：图集是"一年要有365套衣服"，返回"前屈非常简单"）;
3. 返回内容**不稳定**：同一批里第 3/4 条拿到"七月·前屈"，第 5~9 条拿到"姜池池"，说明它取的是**推荐位**。

**根因**（对应 `ytdlp_engine._parse_douyin_via_api`）：

```python
target = next((x for x in items if str(x.get("aweme_id")) == vid), items[0])
#                                                                   ^^^^^^^^ 兜底盲取第一条
```

- 这类链接（图片/图集/live实况图/合集/带声图集）短链展开后是 **`/note/<id>`**，属"笔记"类型；
- 而 `aweme/v1/feed/` 接口**不返回笔记**，它返回的是 5~6 条**推荐视频**，目标 id 不在其中；
- 于是 `next(...)` 落空、**静默回退到 `items[0]`** → 返回一条无关的推荐视频，且不报错。

> 该行上方注释本身写着「不能盲取第一条」，但兜底恰恰就是盲取第一条 —— 逻辑自相矛盾，
> 也说明当时只验证了**视频**类型的链接。

### 3-6 水印核实 + 隐藏 WebView 的副作用（真机，2026-10-06）

#### ① 水印：`downloadUrlList` **带水印，不能用**

把 `tplv-dy-water-v2` 的模板参数做 base64 解码：

```
模板名   ：tplv-dy-water-v2（含 "water"）
参数原始 ：5oqW6Z-z5Y-377yaenozODMyNDE0MTIy
解码结果 ：抖音号：zz3832414122
```

即这个模板会把**"抖音号：xxxx"水印烙在图上**。而 `urlList` 用的模板是
`tplv-dy-aweme-images:q75`，实测取回 **HTTP 200 / 424998 字节 / 真实 webp**。

> **结论：下载必须用 `urlList`，不能用 `downloadUrlList`** —— 否则违背本项目的
> "无水印"卖点。这条推翻了实现前的预设，正是"先验证再动手"的价值。

#### ② 内存：修复前会泄漏，修复后不再累积

`DouyinActivity` 原本**没有任何销毁逻辑**（全仓无 `web.destroy()`）。真机实测：

| 阶段 | 修复前 | 修复后 |
|---|---|---|
| 基线 | 160 MB | 166 MB |
| WebView 解析中 | 261 MB | 263 MB |
| Activity 结束后 | **290 MB（不回落）** | 267 MB |
| 连续解析 3 次 | — | 265 / 271 / 266 MB（**平稳**） |

**修法**：新增 `onDestroy()`，按「停加载 → 切到 about:blank → 从父容器移除 → destroy」的顺序销毁。

残留的约 +100 MB 是 **Chromium 首次载入应用进程的一次性开销**（不是每次解析都涨），
只要用 WebView 就无法避免；关键是**它不再随解析次数增长**。

#### ③ 声音：做了三档防护，但结论要如实说

修前实测确实启动了声轨：

```
I AudioTrack: start(calling package is:com.ytdlp.android, portId:6167, ...)
```

依次加了三档防护：

1. `settings.mediaPlaybackRequiresUserGesture = true`（禁自动播放）
2. `onPageStarted` / `onPageFinished` 注入 JS 补丁：改写 `HTMLMediaElement.play`（强制 muted + volume=0）
   并拦掉 `AudioContext.resume`（防 Web Audio 绕过）
3. `shouldInterceptRequest` 里**直接掐掉媒体请求**（音/视频文件不加载）

**加固后仍能观察到声轨被创建**，但特征与"真的在放"不同：

```
AudioTrack: stop(6170): called with 384 frames delivered   ← 约 8 毫秒
```

每次持续仅毫秒级即停 —— 更像是 WebView 初始化音频子系统（该页面使用 WebRTC，
日志有 `Running WebRTC with a combined Network and Worker thread`），而非持续播放。

另外这台设备（vivo）自带 **AudioHardening**，音频栈里能看到系统主动把本应用的
后台播放静音：

```
AudioHardening background playback would be muted for com.ytdlp.android (10522), level: partial
```

**如实说明**：日志能证明"没有持续播放"，但**不能 100% 证明绝对无声**。
最可靠的确认是用户实际听一次。这一点已记录为待用户确认项。

#### ④ 重复解析 / 状态

- 连续解析 3 次，内存平稳（见 ②），未出现累积；
- `delivered` 标志保证同一次解析只回传一次结果；
- Activity 已加销毁逻辑，实例不会堆着不放。

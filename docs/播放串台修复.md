# 播放区串台修复（解析新视频却播了上一个已下载的文件）

- **日期**：2026-10-04
- **类型**：缺陷修复（用户可见、行为错误）
- **影响端**：Android 端
- **涉及文件**：
  - `android/app/src/main/java/com/ytdlp/android/ui/ParseScreen.kt`
  - `android/app/src/main/java/com/ytdlp/android/engine/Engine.kt`
  - `android/app/src/main/python/ytdlp_engine.py`
  - `android/app/src/main/java/com/ytdlp/android/ui/VideoPlayer.kt`

---

## 一、现象（用户实测反馈）

> 「解析了一个新视频，但播放时它播放的还是之前的视频。播放区旁边有一行字写着
> 『播放已下载的文件』—— 可它不是一个按钮，只是一句说明，却直接播的是之前下载的那个视频。」

即：**解析新视频后，播放区给出了上一个已下载视频的本地文件**。

---

## 二、这个判断是干什么用的

播放区需要决定「播哪一个地址」，优先级是：

1. **本地文件**（`localPath`）—— 不怕直链过期，B站/YouTube 这类纯 DASH 站点只有它能播；
2. **在线直链**（`resolvedUrl`）—— 抖音/X 这类渐进式流的地址；
3. 都没有 → 显示「该站点是音视频分轨流，需下载后才能播放」。

解析结果里**没有** `localPath`（它来自 yt-dlp 的 `info`，而产物路径是下载完成后才记进历史的）。
所以为了让用户「刚下完就能接着播」，`ParseScreen` 里做了一处补丁：

```kotlin
val justDownloaded = download.path.takeIf { download.isDone && it.isNotBlank() }
PlayerBox(video, source = justDownloaded ?: video.playSource)
```

`download` 是**全局**的下载状态：同一时刻只有一个任务，而且**完成后的状态会一直留着**，
直到下一次下载开始或用户点掉下载条。

---

## 三、缺陷是什么

上面那个判断里，**没有任何地方校验「这个产物是不是当前这条视频的」**。

于是只要「下过任意一条」，之后解析**任何**新视频，播放区都会拿到那条旧产物的路径，
把它当成当前视频的播放源 —— 而且因为路径是本地文件，角标还会显示「播放已下载的文件」，
看起来像是应用在说「我播的是已下载的文件」，用户自然认为这是在播当前视频。

用户设备上可以找到对应的历史痕迹：`大型纪录片…[BV1ckhW6DErb].mp4` 是 **9 月 26 日**
就下好的文件，之后解析的每一条新视频都被它顶掉了。

> 注意：这不是「本地文件优先」这条策略的问题。本地文件优先本身是对的（见第二节），
> 错的是**把全局下载状态当成了当前视频的属性**。

---

## 四、具体改了什么

| 文件 | 改动 |
|---|---|
| `ytdlp_engine.py` | `start_download` 时把 `url` 写进下载状态，让状态能表明「这个任务属于哪个视频」 |
| `Engine.kt` | `Download` 增加 `url` 字段（默认空串，不破坏原有构造） |
| `ParseScreen.kt` | 归属校验：`download.url == video.sourceUrl` 才认这条产物 |
| `VideoPlayer.kt` | 按用户要求删掉「播放已下载的文件 / 在线播放」那行角标，并清掉因此失去使用者的 `isLocal` 参数 |

```diff
-val justDownloaded = download.path.takeIf { download.isDone && it.isNotBlank() }
+val justDownloaded = download.path.takeIf {
+    download.isDone && it.isNotBlank() && download.url == video.sourceUrl
+}
```

关于那行角标：它同一个元素有两种文案（`播放已下载的文件` / `在线播放`），
**整个一起删掉**——它只是说明文字、点不动，而用户反馈正是把它当成了按钮说明，
反而加剧了误解。

---

## 五、影响面

**修好了什么**

- 解析新视频时，播放区不再拿上一个已下载的产物当播放源。
- 「同一条视频刚下完就能接着播」这个原有用途**保留**（归属校验通过时才生效）。

**明确不受影响的**

- 历史页播放（`HistoryScreen` 走的是 `video.playSource`，本来就按记录自己的 `localPath`，未改动）。
- 下载链路本身、文件名、画质。

**边界**

- 该状态是**内存态**，不持久化：应用重启后下载状态归零，`justDownloaded` 自然为 null。
- 由此暴露出的相邻问题（**先下载过、之后重新解析同一条视频时，播放区仍提示「需下载才能播放」**）
  不在本次修复范围内 —— 根因是「解析结果不带 `localPath`」，与本次是两回事，另行处理。

---

## 六、验证记录（真机：vivo V2425A / Android 16）

用 `uiautomator` 读取真实界面状态判断走了哪条分支。测试序列：**下载视频 A → 解析另一条视频 B**。

| 检查项 | 结果 |
|---|---|
| 视频 A 自身（刚下完） | 播放按钮存在 = **True**，「需下载后才能播放」= False → 自己的产物仍能播，功能没坏 |
| 视频 B（新解析，不同视频） | 播放按钮 = **False**，「需下载后才能播放」= **True** → 不再串到 A 的产物 |
| 角标文案 | `播放已下载的文件` = **False**（已删净） |
| 下载产物 | 文件名正常：`你的摇杆是怎么坏玩的？… [BV1dcLE6EEce].mp4` |

---

## 七、回滚方式

去掉 `download.url == video.sourceUrl` 这一处校验即可。回滚后：解析新视频又会拿上一个已下载的
文件来播（即本 bug 复现），其余功能不受影响。

---

## 八、教训

一个**全局状态**（下载状态）被拿去回答一个**关于某条具体记录**的问题（这条视频该播哪），
而且这个状态在任务结束后**不会自动清空**。两个条件叠加，就成了「很久以前的一次下载，
持续影响之后每一次解析」。

同类风险的其他位置：`HistoryScreen` 与下载条都读取同一个全局状态，但它们只展示「当前任务的进度」，
不存在"归属"问题，因此未改动。

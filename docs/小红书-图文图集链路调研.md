# 小红书「图文 / 图集 / 实况图」链路调研（2026-10-17）

**性质**：可行性取证 + 设计设想。**本轮没有实现任何代码。**
**口径**：只写实测得到的结论并附证据；没测到的明确写「未证实 / 未取到」，不做推测性结论。

## 一、结论摘要

| 问题 | 结论 |
|---|---|
| 能不能做？ | **能** —— 带登录态时，HTTP 直连笔记页就能拿到图文类笔记的完整数据（含图片直链） |
| 现成 yt-dlp 链路能做吗？ | **不能** —— yt-dlp 的 XiaoHongShu 提取器只取视频格式，图文笔记必然报 `No video formats found` |
| 要不要登录态？ | **要** —— 与视频笔记一致；未登录时页面不下发笔记数据 |
| 图片有无水印？ | 直链模板是 `notes_pre_post`（**没有 `water` 字样**，与抖音那条带水印的 `tplv-dy-water-v2` 不同）；**但「下载后目视确认无水印」未做**（未证实） |
| 最大的坑 | **频控/风控**：请求密了会被送进登录墙，连 yt-dlp 一起被拒 —— 实测踩到 |

## 二、已证实的事实（附证据）

### 2-1 未登录态拿不到任何笔记数据

匿名抓详情页（带不带 `xsec_token` 返回的是同一份 **39,561 / 96,397 字节**的空壳）：

```
note.noteDetailMap = {}          ← 笔记数据根本没下发
user.loggedIn      = false
```

### 2-2 带登录态时，图文笔记数据完整

带一份已登录的 Cookie 抓 `discovery/item/<id>` 页（107,410 字节），`__INITIAL_STATE__` 里：

```
note.type      = normal                     ← 图文（视频是 video）
note 顶层键     = ['atUserList','desc','imageList','interactInfo','ipLocation',
                  'lastUpdateTime','noteId','shareInfo','tagList','time','title','type','user','xsecToken']
imageList 张数  = 1（该条图文）/ 8（图集）/ 13（实况图合集）   ← 后两条被风控打断，未取到结构
note.video     = 无
```

单张图（`imageList[i]`）的字段：

```
key  = ['fileId','height','infoList','livePhoto','stream','traceId','url','urlDefault','urlPre','width']
urlDefault = http://sns-webpic-qc.xhscdn.com/<ts>/<hash>/notes_pre_post/<fileId>…
urlPre     = 同一 fileId、不同 hash 的预览版
infoList   = [{'imageScene':'WB_PRV','url':…}, {'imageScene':'WB_DFT','url':…}]
width/height = 1728 x 2304
livePhoto  = false（该条）
```

### 2-3 图片取流：HTTP 200、JPEG、**不需要 Cookie**

对 `urlDefault` 的取流实测（前 2048 字节）：

```
带 Cookie:   HTTP 200 type=image/jpeg magic=b'\xff\xd8\xff\xe0'（JPEG SOI）
不带 Cookie: HTTP 200 type=image/jpeg magic=b'\xff\xd8\xff\xe0'
```

### 2-4 短链 → 真实笔记地址的两条路

```
分享短链 https://xhslink.cn/o/xxxxxxxx
   └─(302)→ https://www.xiaohongshu.com/login?redirectPath=<urldecode 后就是完整笔记地址，含 xsec_token>
                  └─(带登录态再跳)→ https://www.xiaohongshu.com/discovery/item/<id>?…&xsec_token=…
```

**这条对实现有用**：即使没登录，也能从 `redirectPath` 里解析出真实笔记地址（含 `xsec_token`）。

### 2-5 Cookie 文件里 `#HttpOnly_` 行绝不能被跳过

Netscape 格式里 `#HttpOnly_` 是**合法行**（只是给 cookie 加 HttpOnly 标记），登录态 `web_session` 就在这几行里：

| Cookie 头构造方式 | 实测结果 |
|---|---|
| 跳过 `#HttpOnly_` 行（把 `#` 开头都当注释） | ❌ 302 到 `/login`，页面 39,561 字节、`noteDetailMap` 为空 |
| 保留 `#HttpOnly_` 行 | ✅ 直达笔记页，107,410 字节、有数据 |
| 只发 `web_session` 一条 | ✅ 也能直达，80,051 字节、有数据 |

（yt-dlp 自己的 cookiejar 会正确处理该前缀，所以它不受影响 —— 这也解释了「yt-dlp 能过、自己拼请求头却过不去」的差异。）

### 2-6 频控/风控：当前正在发生的拦阻

时间线（同一条 video 短链、同一份 Cookie）：

```
02:0x  带 Cookie 解析成功（yt-dlp 拿到 4 个格式）
02:2x  图文图集那条 → 最终地址变成 https://www.xiaohongshu.com/website-login/captcha（验证码页）
02:3x  全部请求 → https://www.xiaohongshu.com/login（39,560 字节空壳）
02:47  yt-dlp 也报 Unsupported URL（同样被送到 /login）—— 不是 yt-dlp 的问题
```

- Cookie **没有过期**（`web_session` 有效期剩余 8,759 小时，约 365 天）。
- 因此拦阻来自**平台侧的频控/风控**，而不是凭据失效。**具体触发阈值未证实**（只知「短时间内十几次请求」会触发）。

## 四、如果要做，可行的实现形态（设计，非实现）

**方案 A（推荐）：在引擎里加一条「小红书图文兜底」**

```
触发点：平台 == 小红书 且 yt-dlp 报 No video formats found
步骤：① 跟随短链（带 Cookie）拿到真实笔记地址（也可走 redirectPath）
      ② GET 笔记页 → 取 window.__INITIAL_STATE__
      ③ 读 note.noteDetailMap[<id>].note
      ④ type == normal → 取 imageList 里的 urlDefault（展示/下载同一份即可）
      ⑤ 逐张下载图片（GET 即可，不需要 Cookie；文件名用「标题 + 序号.jpg」）
```

- **改造面与 1.0.4 抖音图文那次同构**：数据模型（一条记录对应多个产物，而不是一个视频）/ 界面（图集展示，没有播放概念）/ 下载（多文件 + 进度）/ 历史（一条记录、多份产物）。
- **必须做的两件事**：
  - 用与 yt-dlp 同一份 `cookiefile`（或自己正确解析 `#HttpOnly_`，见 2-5）；
  - **识别风控**：最终地址含 `/login` 或 `/website-login/captcha` → 明确提示「平台要求重新登录/稍后再试」，而不是报「该站点改版了」。
- **建议节流**：同一会话内限制请求频率（本次实测的触发条件就是请求过密）。

**方案 B：WebView 兜底** —— **不建议**。小红书笔记页是服务端渲染（数据就在 HTML 里），HTTP 直接取就够；WebView 更重，而且照样会被风控。

**方案 C：不做，如实报错** —— 可接受的理由：图文类必须登录态、又要面对风控，而当前提示（[PLATFORM_ERROR_HINTS「小红书」](../android/app/src/main/python/ytdlp_engine.py)）已经能把用户引到正确方向。

## 五、代价与风险（如实列出）

1. **必须登录态**：与视频一致，用户不导入 Cookie 就用不了。
2. **风控**：实现后仍可能被拦，必须给可操作的提示 + 限频；不能承诺「一定成功」。
3. **图片 CDN 是 `http://`（明文）**：应用已开 `usesCleartextTraffic`，能取流；但这属于 1.0.4 报告 A3 那条「全局明文」的既有取舍范围。
4. **图片来源合规**：图集类内容多是个人笔记，默认应与视频同样的「个人使用」口径。

## 六、风控机制与替代路径（公开资料调研，**非本次实测**）

> 本节由专门跑爬虫逆向的子代理查公开资料得出，**每条都标了确定度与来源**。
> 凡是「社区经验」，都不能当事实用 —— 后面要用实测校准。

### 6-1 风控和哪些东西绑定

| 结论 | 确定度 | 来源 |
|---|---|---|
| `x-s` = `a1` cookie + 请求路径 + body + 时间戳，纯算法可算 | 确定（有 MIT 公开实现） | [xhshow](https://github.com/Cloxl/xhshow) |
| `x-s-common` 里 x5 依赖 cookie 的 `a1`，而 x8/x9 依赖 **localStorage 的 `b1`** | 确定（该参数表被广泛引用） | [segmentfault 校验流程](https://segmentfault.com/a/1190000042799981)、[lobehub 参数表](https://lobehub.com/pt-BR/skills/omnimasudo-seraphyagent-xiaohongshutools) |
| `gid` + `timestamp2` 是**设备校验态**；`web_session` 才是登录态；`websectiga` / `acct` 是设备 / 账号风控指纹 | 确定 | 同上 |
| 频率经验值：同 IP >30 次/分 → 临时封；同账号 >500 次/时 → 风控；对**同一笔记**高频访问 → 验证码；限流一般**数小时~24 小时自解**，切 IP 可缓解；账号级要停 3~7 天 | **社区经验，未证实** | [CSDN 教程](https://blog.csdn.net/mz159_357/article/details/154903630)、[社媒助手风控说明](https://smzs.xisence.com/help/faq/xiaohongshu/risk-control)、[gujiakai 博客](https://blog.gujiakai.top/2024/09/xiaohongshu-rss-tips.html) |

**对我们的直接含义**：`x-s-common` 需要 localStorage 里的 `b1`，**纯 HTTP 客户端先天拿不到** —— 走「内部接口 + 自己算签名」这条路在签名上就有先天缺陷（要么凑一个默认值碰运气，要么把 JS 环境搬进来）。

### 6-2 替代路径对比（含取舍）

| 路径 | 需要什么 | 成本 / 风险 | 取舍 |
|---|---|---|---|
| **① SSR 页面 + 用户 Cookie**（我们现方案） | 登录态 + 合理请求头 + 节流 | 会被频率风控；不需要签名 | ✅ **主路径**：实现最轻、下游全可复用 |
| ② web 内部接口 `edith.xiaohongshu.com/api/sns/web/v1/feed` | `x-s` / `x-s-common` / `x-t`，feed/搜索还要 `x-rap-param`，详情要 URL 里的 `xsec_token` | 签名算法要自己维护；`x-s-common` 的 `b1` 纯 HTTP 拿不到 | ❌ 不选 |
| ③ 移动端 App 接口 | `shield`（aes128+hmac_md5）+ 设备指纹 / 通用参数 | 成本最高、要模拟设备态 | ❌ 不选 |
| ④ **真机 WebView**（拦主文档 / 接口响应） | 把用户 Cookie 注入 WebView 后加载笔记页 | 指纹与 IP 都是真实设备；「是否更宽松」**无公开量化数据（未证实）** | 🅱 备选 / 兜底（基建已有） |
| ⑤ 第三方服务 | 依赖别人的服务 | 不可控、可能收费/限流 | ❌ 不选 |

参考：RSSHub 的做法是**真实浏览器**（Playwright/CDP）注入页面 JS、拦资源，遇验证码抛 `CaptchaError`，靠 `XIAOHONGSHU_COOKIE` 注入并强控速 —— [来源](https://deepwiki.com/DIYgod/RSSHub/6.6-web-scraping-with-puppeteer)。**这等于「④ 真机 WebView」的桌面版**，说明浏览器路线是社区主流做法之一。

第三方文档称动效视频在 `imageList[i].stream` 或 `imageList[i].video`，静图在 `infoList[WB_PRV/WB_DFT]`（[istero 字段样本](https://api.istero.com/blog/detail/32314161)、[Apify 抓取器](https://apify.com/zen-studio/rednote-search-scraper)）。
我们自己的取证只能确认：该字段**存在**（`imageList[0]` 的键里就有 `stream`），但抓到的那条 `livePhoto=false` → **必须实测一条真实况图**才能定案。

### 6-4 最小验证实验协议（只发 2 次请求，间隔 ≥60 秒）

| 步骤 | 请求 | 要点 |
|---|---|---|
| 1 预热 | `GET https://www.xiaohongshu.com/` | 带 UA + `Accept` + `Accept-Language` + `Sec-Fetch-*`，让页面下发 `a1` / `gid` / `websectiga` |
| 2（≥60 秒后） | `GET` 目标笔记页 | **同进程复用第 1 步拿到的 cookie**；头与前一步一致，补 `Referer: https://www.xiaohongshu.com/`、`Accept: text/html` |

判读：

- 返回**验证码页**（`/website-login/captcha`）→ 频率 / 行为风控
- 返回**登录空壳**（`/login`，约 39,560 字节、`noteDetailMap` 为空）→ 会话 / 账号 / IP 已被标记
- 返回**完整页面**（`noteDetailMap` 有数据）→ 之前是「会话预热 / 请求头不足」的问题

> 本次实测的教训正好对上第 3 点的一半：我们当初只发了 `UA + Accept-Language + Cookie`，**没有预热、没有 Referer、没有 Sec-Fetch-\***。

## 七、策略结论（本轮定下来的路线）

1. **主路径：SSR 页面 + 用户导入的 Cookie + 会话预热 + 节流**。不引入签名、不模拟设备态 —— 代价最低，且和手机用户的真实环境最接近。
2. **风控必须当成一等公民处理**：请求间隔设下限（建议同会话 ≥ 60 秒）；识别 `/login` 与 `/website-login/captcha` 两种地址，给「平台要求验证 / 稍后再试 / 重新导入 Cookie」这类可操作提示，**不许**再落到「该站点可能改版了」。
3. **兜底：真机 WebView**（复用 `DouyinActivity` 的「拦主文档 + 静默 + 超时」基建），把用户 Cookie 注入 WebView 再加载笔记页 —— 指纹与 IP 最真实。
4. **明确不做**：x-s / shield 自算签名、移动端 App 接口、第三方服务。

## 八、真机实测（2026-10-17）：被拦的根因不是 IP，而是这份会话

**做法**：装 1.0.6 包 → 设置页导入 Cookie（界面确认「已导入：`/data/user/0/com.ytdlp.android/files/cookies.txt`」）→ `ACTION_SEND` 投喂视频短链 `https://xhslink.cn/o/20h2VnYVJmg`。

**结果**（手机界面原文）：

```
解析失败
小红书需要登录态：不带 Cookie 时，分享短链会被跳到登录页…
原始报错：ERROR: Unsupported URL: https://www.xiaohongshu.com/login?redirectPath=…

提示：Cookie 可能已过期。请重新导出并导入 —— 导出前要确保浏览器里处于登录状态。
```

**结论**：

- **手机（真实设备、不同 IP、Cookie 已导入）与 PC 表现完全一致** → **排除了「PC 环境/IP 被标记」这个假设**。
- 更贴合的解释：**这份会话（`web_session`）被平台标记**，凡带它的请求一律被送到登录页。与社区经验「限流一般数小时~24 小时自解」吻合。
- **未证实（要靠新的 Cookie 再测）**：① 重新导出的一份 Cookie 是否立刻可用；② 补齐请求头 + 会话预热能否降低触发概率。

**顺带修掉一个我们自己的文案 bug**：原提示写「不带 Cookie 时…」，而用户明明已导入 Cookie —— 会让人以为是自己没导入。现改为把两种成因并列（没导入 / 登录态被要求重新验证 / 平台限流隔几小时再试）。

## 九、本质：为什么会被「登出」，而不是「限流」

**用户实测反馈（2026-10-17）**：小红书 **web 端与手机客户端同时被登出**。这不是限流（限流只是单次请求被拒），是平台**主动吊销了这份登录态** —— 账号级处置，换设备也一样。

成因按可能性排序（结合本轮全部实测 + 逆向 SOP 里的反爬工程要点）：

1. **TLS 指纹（JA3）与 UA 不一致 —— 最可能的主因。** 我们的请求是 Python 的 TLS 栈（urllib / yt-dlp），却带着 Chrome 的 UA。反爬系统用 JA3 指纹一眼就能认出「这不是浏览器」。SOP 里明写了这条：`requests` 类库需用 `curl_cffi` 等模拟真实浏览器 TLS 指纹。
2. **缺少浏览器上下文。** `x-s-common` 的 x8/x9 依赖 **localStorage 的 `b1`**（纯 HTTP 拿不到）；`websectiga` / `a1` 这类指纹 cookie 与真实浏览器环境本就不一致；再加上我们的请求**没有预热、没有 `Referer`、没有 `Sec-Fetch-*`**。
3. **高频 + 盯同一条。** 一小时内 15+ 次请求，且反复访问同一条笔记。

三者叠加 → 平台判定「这份会话正在被自动化使用」→ **强制登出**。

**架构层结论（比技术细节更重要）**：

> 「用户从浏览器导出 Cookie → 应用拿去做裸 HTTP 请求」这条路**本身脆弱**。它不属于「调参就能调好」的问题 —— 任何一次请求量上来都可能导致**用户自己被登出**（浏览器与手机 App 的登录态一起失效），代价远大于一次解析失败。

**最硬的一条证据（真机，第二轮）**：用户重新登录、导入了那份**全新** Cookie 之后，应用发出的**第一条**自动化请求就被送进验证码页：

```
ERROR: Unsupported URL: https://www.xiaohongshu.com/website-login/captcha?redirectPath=…
```

即：**换新会话也救不了** —— 被拦的是「这类请求本身」（非浏览器 TLS 指纹 + 缺 localStorage 的 `b1` + 没有会话预热），而不是「这份会话」。这条直接否掉了「让用户多导几次 Cookie」的思路。

## 十、另谋出路：全量选项与已定顺序

用户确认的**试探顺序**：**先实测第三方解析服务 → 不行再测 TLS 指纹对齐 → 最后 WebView；也可以几种搭配使用。**

| # | 方案 | 用户额外操作 | 我们的成本 | 实质 / 风险 |
|---|---|---|---|---|
| 1 | **第三方解析服务**（照 `x_fallback.py` 那条链路写：一个 HTTP 请求 → 统一记录字段） | **零** | **极低**（代码形状可直接搬，甚至能当主路径） | 依赖别人：可用性/限流/收费、笔记链接要经过它的服务器；**是否有可用服务待实测** |
| 2 | **应用内 WebView 登录一次 + 拦主文档** | **一次登录**，之后零操作 | 一个 Activity（`DouyinActivity` 那套可大量复用）+ 一个 SSR 解析器 | 自主可控；会话留在应用 WebView，指纹/IP/设备全一致 |
| 3 | 自建解析服务（RSSHub 式：服务器上跑真实浏览器） | 零 | 最高（服务器 + 维护 + 自己对抗风控） | 用户笔记经过自己的服务器（隐私）；只有做成多用户产品才划算 |
| 4 | TLS 指纹对齐（安卓 OkHttp 自定义 TLS 近似 Chrome JA3；Python 侧 curl_cffi 在 arm64 无现成轮子） | 不变（仍要导 Cookie） | 中 | **治标**：只降低被判定概率，不解决「用户被登出」 |
| 5 | 保持现状（只做视频 + 如实提示） | 导 Cookie（易失效） | 零（已完成） | 仍是那条脆弱链路 |
| 6 | 移动端 App 接口 + shield 签名逆向 | **仍要登录态**（App 接口要用户 token） | 最高（jadx + Frida + 设备指纹还原） | 花最大成本换来同样的「要登录」 |

**必须澄清的一点**：方案 2 不是「更麻烦」，而是**比现在更省事**。

```
现在的流程：浏览器扩展导出 cookies.txt → 传到手机 → 应用里选文件 → 被标记后重来一遍
WebView 流程：点一次链接 → 在应用里登录一次 → 之后长期有效
```

所以「对用户不友好」这个担心，指向的是**现在这套**，不是 WebView。

**明确不选**：方案 4 只治标；方案 6 花最大成本却换不来友好度。（方案 4 仍保留为方案 1 失败后的次选，按用户确认的顺序。）

**第三方服务方案的红线（无论选哪家）**：① **绝不把用户的 Cookie 发给第三方**；② 走这条路时应用只发一个普通 HTTP 请求，解析失败要给可读原因（照 `x_fallback.py` 的错误分层：服务故障 / 这条没有媒体 / 限流）。

## 十一、最终结论：走「应用内 WebView」，已实现并真机验证

三条候选路径都实测过之后的定论：

| 路径 | 实测结果 | 结论 |
|---|---|---|
| 第三方解析服务 | 付费托管服务（EasyDown / TikHub / Apify）**全都要 key**，免费聚合接口**一个都没通**；且用户链接要经过别人的服务器 | ❌ 未采用 |
| TLS 指纹对齐 | 方向对（你 skill 里 `anti-bot-notes.md` 的第一条就是它），但**要验证必须用登录态发请求**（会再次连累账号），安卓端还要改 OkHttp 的 TLS 配置 —— 治标 | ❌ 未采用 |
| **应用内 WebView** | 真实 Chromium 环境，平台视为正常用户；数据直接从页面变量取（SSR） | ✅ **采用** |

**代价（用户已知情并接受）**：小红书限制同时登录的设备数 —— 在应用里登录后，**用户电脑网页端的会话会被挤下线**（实测提示「电脑设备登录超限」）。这句话已写进登录页文案，用户当场就能看到再决定。

**同时定下的两条**：① 小红书**不再使用导出的 Cookie**（那条路会把用户账号送进风控），`use_cookies` 两端都改成 false；② **合集类笔记优先给图集**（平台把笔记合成成视频、但带着一整组图的，按图集给 —— 实测判据：真正的视频笔记只有 1 张封面图）。

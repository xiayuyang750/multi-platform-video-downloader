# 水印工坊 · 支付接入方案调研与实施建议

> 用途：v1.0.7 前置调研。回答「要不要办执照、要哪些资质、别人为什么看起来不用这些也能收款、我们该怎么走」。
> 性质：技术与商业方案分析，**不构成法律意见**。涉及主体资质、侵权认定、税务的具体结论，请以支付机构审核口径和执业律师意见为准。
> 文中标注「待核实」的条目，是需要在办理前向微信支付/支付宝/当地市场监管确认的事实。

---

## 〇、一句话结论

现在真正卡住的**不是技术，也不是服务器**，而是两件事：**经营主体资质** 和 **产品类目的合规性**。

- 想「付款 → 自动到账 → 自动发密钥」且长期稳定：**必须有个体工商户或企业执照**，走微信/支付宝官方 App 支付。个体户够用，不必须开公司。
- 不想现在办执照：走 **发卡平台 + 兑换码**，不需要任何资质，1~2 天能上线，代价是平台抽成与平台自身被清退的风险。
- **个人收款码自动监听（免签支付）、第四方代收、商户号租用**：看起来能用，实际是违规通道，不推荐。

## 一、现状（代码事实）

| 项 | 现状 |
|---|---|
| 授权方式 | 一机一码，`server/worker.js` + Cloudflare KV |
| 已实现接口 | `/api/activate`、`/api/verify`、`/admin/api/*` |
| 试用策略 | 3 次，第 4 次拦截（`LicenseStore.kt`） |
| 发码方式 | **人工**：后台生成密钥 → 手动发给用户 |

结论：**发码已经是自动的（服务端签发 token），缺的只有「收款」这一环。**

## 二、先回答四个具体问题

### 1）必须走企业营业执照吗？

| 通道 | 是否必须执照 | 说明 |
|---|---|---|
| 微信支付 App 支付 | **是**（企业 **或个体工商户**） | 自然人不能申请商户号。个体户可结算到经营者本人账户 |
| 支付宝 App 支付 | **是**（企业 **或个体工商户**） | 个人开发者身份可创建应用，但「APP 支付」产品需签约主体资质 |
| 第三方发卡平台 | **否** | 你只是商品方，收款主体是平台 |
| 个人收款码 | **否** | 但没有回调，无法自动发码；且用于经营远程收款受限制（见第四节） |

**结论：不需要「公司」，但需要「执照」。** 个体工商户是目前成本最低的合规主体。

### 2）需要「平台应用审核」吗？

需要。微信开放平台/支付宝开放平台都要求：

- 创建移动应用，填写 **包名 + 应用签名**（Android）
- 提交应用截图、功能说明、官网或下载地址
- 申请「App 支付」产品并签约
- 微信开放平台开发者认证（企业/个体户，约 300 元/年，**待核实**当期价格）

**这是本方案最大的不确定点**：工具类、尤其「去水印/下载类」应用，审核口径偏严，可能被要求提供应用商店上架证明，或被直接判定类目不符。**在办执照之前，建议先用现有包名/签名提交一次应用审核试探口径**（免费，不通过也能拿到理由）。

### 3）必须备案域名吗？

分情况：

- **App 支付的服务端下单/查单**：服务端主动 HTTPS 调用支付机构接口，**不强制 ICP 备案**；Cloudflare Worker 可以出站访问微信/支付宝（二者都在境内，出站没问题）。
- **支付回调**：支付机构从境内发起回调到你的地址。`workers.dev` 在大陆不可达，回调大概率超时 → 需要「境内可达入口」，或改用**主动查单**替代（见第七节）。
- **H5/JSAPI 支付**：明确要求已备案域名，且与商户主体一致。我们只做 App 支付，可绕开这一条。

**结论：备案域名不是绝对前提，但「回调地址境内可达」是。** 最省事的解法是主动查单，不依赖回调。

### 4）为什么别人「没备案、没上架」也能收款？

因为「能收到钱」和「合规」是两件事。常见四种机制（详见第四节），其中三种有明确风险。

## 三、四条路线对比

| 路线 | 资质 | 自动化程度 | 现金成本 | 合规风险 | 工作量 |
|---|---|---|---|---|---|
| **A. 个体户 + 官方 App 支付** | 执照 + 商户号 + 应用审核 | 全自动 | 执照代办 300~800、记账 2000~3000/年、认证 ~300/年、费率 ~0.6%（**待核实**类目费率） | 支付侧低；**类目审核与版权风险仍在** | 资质 1~3 周 + 开发 3~5 天 |
| **B. 发卡平台 + 兑换码** | 无 | 半自动（平台发货给你码，App 内兑换） | 平台抽成约 3%~10% | 中：平台自身合规性、封店、资金不到账 | **1~2 天** |
| **C. 个人收款码 + 人工发码** | 无 | 手工 | 0 | 高：违反支付服务协议、无交易凭证、易被风控 | 0.5 天 |
| **D. 第四方代收 / 免签 / 跑分** | 无 | 全自动 | 高抽成、随时跑路 | **极高：二清、非法经营、资金冻结** | 不建议评估 |

**推荐路径：先 B 验证付费意愿，再 A 承接稳定销量。** 两步之间不冲突：B 产出的兑换码与 A 产出的密钥可以共用同一套激活链路。

## 四、「他们能收款」到底是哪种机制

### 1）个人收款码 + 免签监听

原理：挂一台设备监听微信/支付宝的到账通知（通知栏、无障碍、短信转发），监听到金额后调自己的服务端发货。

风险：
- 违反微信/支付宝收款服务协议，账号可能被限制收款
- 央行 259 号文要求个人静态收款码原则上不得用于远程非面对面收款 —— 这正是本场景
- 无交易凭证、无退款能力、无法对账，用户投诉无据可查
- 金额相同即无法区分订单，容易发错货

### 2）第三方发卡 / 虚拟商品平台

原理：用户付给**平台的商户号**，平台按订单把「卡密/兑换码」发给你和用户，平台再与你结算。用户看到的收款方是平台或其关联公司。

- 这是最接近「个人也能自动卖卡密」的合规边缘方案
- 但虚拟商品、工具类目属于支付机构重点清退对象；平台被封会导致已售码无法兑换、余额无法提现
- 「显示某个公司名」通常就是平台方的收款主体，**不代表你有资质**

### 3）第四方 / 聚合支付「代收」

原理：借用他人商户号收款，再二次清算给你。用户看到的是某个壳公司名。

- 出租/出借商户号、二次清算（二清）被支付监管明确禁止
- 资金在他人账户里，跑路、冻结、被查都是常态
- 情节严重的可能触及非法经营

### 4）商家自有商户号（合法）

就是路线 A。用户看到的收款方是你自己的营业执照主体 —— 这才是「显示公司名」的正当版本。

> 判断标准很简单：**收款主体是不是你自己（或你明确签约的平台），资金有没有经过无资质第三方的手。** 显示公司名 + 自动到账，并不能证明合规。

## 五、法律与合规风险（比支付本身更要紧）

### 1）版权与「去水印」的定性

- 水印通常属于《著作权法》意义上的**权利管理信息**；该法第五十三条将「未经许可故意删除或者改变权利管理信息」列为侵权行为（有技术原因不可避免等例外）。
- 绕过平台技术措施（签名、风控、防盗链）存在被认定为「避开技术措施」的风险。
- 平台方民事路径更现实：用户协议禁止未授权下载/去水印；平台可依《反不正当竞争法》第十二条主张妨碍其产品或服务正常运行。国内已有平台起诉去水印类工具的民事案件，多被认定为不正当竞争。
- 刑事风险（《刑法》第二百一十七条侵犯著作权罪）通常要求「以营利为目的 + 违法所得/情节达到标准」，且多针对**批量搬运、售卖盗版内容**；单纯工具本身的入罪门槛较高，但**收费会显著加重「营利目的」的认定**。

### 2）可控与不可控

| 可控（产品设计） | 不可控（外部） |
|---|---|
| 不提供付费内容、会员内容、付费墙后内容的下载 | 平台随时改接口、发函、起诉 |
| 不内置绕过登录/付费的「破解」能力 | 应用商店类目拒绝（国内商店基本不收此类工具） |
| 不提供批量采集 API、不做内容二次分发 | 支付机构类目审核拒绝 |
| 用户协议写明「仅用于个人备份已公开内容」 | 监管口径变化 |

**结论：收费不会让工具本身变成「必然违法」，但会把「个人使用的合理使用抗辩」削掉一大截，并让平台维权更有动力。** 这一点需要在商业决策里被明确接受，而不是当作技术细节。

### 3）税务

有经营收入就应申报。个体工商户可核定征收，成本远低于公司；但「用个人码收经营款不申报」属于另一类风险，不要用它换取短期便利。

## 六、推荐路线（分阶段）

### 阶段 0：现在就能做（不依赖任何资质）

- 保留人工发码，把「购买」入口做进 App：展示价格 + 复制设备码 + 联系方式，用户付款后你发码
- 同时把**兑换码/密钥自助兑换**做出来（见 7.1），后续无论走 B 还是 A 都能复用

### 阶段 1：B 方案，验证付费（1~2 天开发）

- 在发卡平台挂「水印工坊授权码」商品，自动发货内容是兑换码
- App 内新增「兑换码」入口，兑换后自动绑定当前设备
- 观察 1~2 个月：转化率、退款率、平台是否稳定

### 阶段 2：A 方案，转正（资质到位后）

- 注册个体工商户 → 开对公/个体户结算账户 → 申请微信支付商户号 + 支付宝商家账号
- 开放平台创建应用 → 签约 App 支付（先用现有包名试探审核口径）
- 服务端实现下单、查单、发货、退款；客户端拉起支付
- 逐步把发卡平台降级为备用渠道

### 不建议做

- 个人码免签监听
- 租用/购买他人商户号
- 第四方代收、跑分
- 为「绕过类目审核」把商品伪装成其他品类（会被判违规，且资金可被冻结）

## 七、技术方案

### 7.1 兑换码模式（阶段 0~1 共用）

**数据**（建议从 KV 迁到 D1，理由见下）：

```sql
CREATE TABLE redeem (
  code        TEXT PRIMARY KEY,   -- RC-XXXX-XXXX-XXXX
  batch       TEXT NOT NULL,      -- 批次号，便于对账
  license_key TEXT,               -- 兑换后生成的正式密钥
  used_by     TEXT,               -- 绑定的设备码
  used_at     INTEGER
);
```

**接口**：

- `POST /api/redeem` `{code, device}` → 原子占用兑换码 → 生成正式密钥 → 绑定设备 → 返回 token（复用现有 activate 的签发逻辑）
- `POST /admin/api/redeem/batch` `{count, batch}` → 批量生成，导出 CSV 交给发卡平台

**为什么不能留在 KV**：KV 最终一致、无原子 CAS，同一个码被并发兑换可能双发。D1 用一条 `UPDATE redeem SET used_by=? WHERE code=? AND used_by IS NULL` 即可保证一次性。

**客户端改动**：`LicenseDialog` 增加「我有兑换码」输入框（现在只有密钥）。兑换成功后写入 `LicenseStore`，与激活流程完全一致。

### 7.2 官方 App 支付（阶段 2）

**订单表**：

```sql
CREATE TABLE orders (
  out_trade_no TEXT PRIMARY KEY,  -- 我方订单号（幂等键）
  device       TEXT NOT NULL,
  sku          TEXT NOT NULL,
  amount       INTEGER NOT NULL,  -- 分，服务端定价，不信客户端
  status       TEXT NOT NULL,     -- created/paid/refunded/closed
  license_key  TEXT,
  created_at   INTEGER,
  paid_at      INTEGER
);
```

**链路**：

1. App 传 `device + sku` → 服务端建单 → 调统一下单 → 返回唤起参数
2. 支付完成后：**回调验签 + 主动查单双保险**，同一 `out_trade_no` 幂等发货（生成密钥并绑定设备）
3. 退款：退款结果回调 → 订单置 `refunded` → 密钥停用或解绑

**回调可达性**：`workers.dev` 境内不可达，但支付机构回调从境内发出，基本连不上。两条对策：

- **首选：主动查单**。用户支付后回到 App 时，客户端请求服务端 `POST /api/order/query`，服务端去支付机构查单并补发货。延迟几秒，可接受，且完全绕开回调。
- 次选：部署境内可达的入口（备案域名 + 反代/轻量服务器）专收回调。

**签名实现**：微信支付 v3 用商户私钥签名 + 平台证书验签；支付宝用 RSA2。两者都可以在 Worker 里用 WebCrypto 实现，私钥放 Secrets，**绝不进 App**。需注意微信平台证书轮换。

### 7.3 防刷与对账

- 一码一次、一码一设备；同 IP/同设备限频
- 金额只认服务端定价
- 每日拉支付机构账单核对订单，差异告警
- 退款政策写进用户协议（虚拟商品是否可退必须先定，否则纠纷无据）

## 附：与「3.3 支付 SDK」原文的差异

原开发总结里写的是「支付回调需要公网可达的服务端；Cloudflare Workers 国内不可直连，需要额外方案」。

实际情况更细：

- **下单/查单是出站调用**，Worker 可直连支付机构，不受「境内不可达」影响
- **回调是入站**，Worker 确实收不到，但可以用**主动查单**替代，不是硬阻塞
- 真正的门槛是**主体资质 + 类目审核**，服务器不是

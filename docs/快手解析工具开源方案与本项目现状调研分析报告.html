1三条结论

结论一 · 快手是「页面内嵌状态」型平台
抖音的公开解析几乎必须解决 a_bogus 签名，快手不用——作品数据直接内联在详情页 HTML 的 <script> 里 （移动端 window.INIT_STATE，PC 端 window.__APOLLO_STATE__）。 单条作品解析可以做到零签名、零登录、纯 HTTP。近两年只做单作品解析的项目，全部走这条路。 你的项目已经踩对了，见第 5 章。
结论二 · 快手「实况图」的动效，开源圈没有一家做出来
这不是"没人研究"，而是网页 SSR 层根本不提供。我用六份独立实现做了交叉验证： 连专门设计了 livePhotoUrl 字段的库（gumphp/video-parse），在快手这条链路上也把字段空着不填。 详见第 4 章。这意味着你反复尝试的方向不是"没找对字段"，而是这个数据源里就没有。
结论三 · 你的缺口比想象的小得多：一个空字符串
审查发现你的数据模型与 Kotlin 侧已经完整支持 live 字段： Engine.kt 读它、content_type 有 "live" 枚举、抖音和微博都已经在填。 快手只是没填——缺口精确到 _ks_atlas_media() 里那行 "live": ""。 不需要动数据结构，不需要动 UI，不需要动 Kotlin。

3技术路线解剖

五条路线，按「在你的技术栈上能不能落地」重新排序。

A · 页面内嵌状态注入 主路 · 你已在用

快手把服务端渲染的状态机直接写进 HTML：移动端落地页 window.INIT_STATE， PC 详情页 window.__APOLLO_STATE__。拿到 JSON 就等于拿到整个作品对象。

两个必须处理的坑

坑一：JSON 里可能有非法片段。会出现被二次字符串化的畸形数据、匿名函数、尾逗号。 方案是「先常规解析，失败再清洗」双保险。media-parser 更稳——手写括号配对扫描器，逐字符计数 {} 并处理字符串转义，精确截取对象边界。

坑二：顶层 key 被位移混淆。tusjoh 是 string 逐字符 +1 的结果。 所以不能按固定路径取值，要么按前缀过滤，要么深度遍历找特征节点（同时含 result 与 photo，或 photoId 与 photoType）。后者抗变更最强。

短链还原的精细做法

// wujunwei928/parse-video · parser/kuaishou.go
client.SetRedirectPolicy(resty.RedirectPolicyFunc(func(req *http.Request, via []*http.Request) error {
    // 只跟随 /short-video/{id} 形态的跳转，其余中断以捕获 Location
    if matched, _ := regexp.MatchString(`^/short-video/[^/]+/?$`, req.URL.Path); !matched {
        return resty.ErrAutoRedirectDisabled
    }
    return nil
}))

// 关键：长视频（短剧）路由返回结构不同，统一改写为 photo 路由
locationUrl = strings.ReplaceAll(locationUrl, "/fw/long-video/", "/fw/photo/")

这个 /fw/long-video/ → /fw/photo/ 的改写是最容易漏的兼容点—— 短剧/长视频与普通视频走两套数据结构，只按普通视频字段取会全空。

B · 内部接口 + Cookie 你这条路上有个硬门槛

KS-Downloader 是这个路线的标杆，不做页面解析，直接打内部接口：

# source/request/detail.py
self.api = "https://live.kuaishou.com/live_api/profile/feedbyid"
self.params = {"photoId": detail_id, "principalId": user_id}
self.extract_keys = ("data", "currentWork")
代价它的解法你能否照做
必须带 Cookie从浏览器读，且注明「无需登录」（游客态即可） 可以 但要自己做 Cookie 获取/续期
TLS 指纹校验curl_cffi + impersonate="chrome146" 复刻浏览器 JA3 很难 Chaquopy 没有 curl_cffi 轮子
请求头语义严格固定 Origin + Referer: /new-reco 可以 纯 header，无成本
对你的具体约束（第 5 章详述）
你的 Android 端是 Chaquopy 嵌入 Python，site-packages 里只有 attrs / retrying， 没有 requests，更没有 curl_cffi，请求全靠 stdlib urllib。 所以「TLS 指纹模拟」这条路对你是关着的，只能靠「标准 TLS + 完整头 + 游客 Cookie」硬试。

再往上：签名 __NS_hxfalcon（sig4）

  • 接口：POST /rest/v/profile/feed、/rest/v/search/feed，query 必须带 ?__NS_hxfalcon={sign}&caver=2；
  • 语义：result=1 成功 / 2 风控限流 / 50 缺签名；
  • 签名绑定请求体、时间窗、设备指纹，不可复用，每次重试都要重算；
  • 形态是 HUDR_****$HE_****，藏 Webpack 的 Jose 模块 + JSVMP 虚拟化保护。

结论：只在做「主页批量 / 关键词搜索」时才需要。你只做单条解析，直接绕开——这是产品设计上的重要取舍。

C · 浏览器驱动 兜底，不是主路

videodl 的分层值得借鉴：按顺序尝试 [DrissionPage] → [requests]，前者拿到有效直链就短路。 浏览器模式只做三件事：打开页面、取 <video> 的 src、取 [poster] 作封面。 加固手段是关掉 AutomationControlled 特征、静音、随机端口。

顺序别抄反
videodl 是「浏览器优先」，因为它要兼容几十个平台。你只做单平台，不该这样—— 浏览器冷启动 2–5 秒、内存 300MB+、并发上不去。 正确顺序是 HTTP 优先、浏览器兜底，且兜底结果要缓存映射。 MediaCrawler 更彻底：浏览器只用来「算签名 / 拿 Cookie」，抓数据仍走 HTTP。

D · MITM 代理嗅探 桌面端专属

res-downloader（20.7k★，Apache-2.0）不做解析：起一个本地代理，让用户把系统代理指过来， 解密流量、从响应里识别媒体资源。两个设计值得看：

core/rule.go —— 规则化 MITM 白名单。 不是所有域名都解密（性能和风险都不允许）。支持 *.domain 通配、! 否定、* 全量； shouldMitm(host) 返回 true 才解密，否则纯透传。让「抓快手但不抓网银」成为可实现的产品能力。

core/middleware.go —— 单端口同时承载控制 API 与代理流量。 /api/preview 单独放开 CORS 且不限方法，说明预览是它的第一等需求，不是下载。

适应性极强：平台改版、加签名、换域名都无所谓，因为地址是从真实播放流量里捡的，天生免疫接口变更。 代价是装根证书、手动配代理、移动端体验差——所以对你 Android 客户端不适用，但对你那个未同步的 Windows 端是个选项。

E · 第三方 SaaS 解析 应急车道

社区里有一批只卖接口的服务（video.zacao.top、云析这类），普遍宣称覆盖「抖音快手图集实况」。 对自研没有技术借鉴价值，但有一个产品价值：作为新形态的临时兜底。 前提是接口契约抽象好，切换成本才低。

但别把它当长期方案
这类服务的稳定性与合规性你无法控制——它挂了或改政策，你的产品跟着挂。 兜底应该用你自己可控的第二条技术路线，而不是第二家公司。

4实况图专项：一个已被证否的方向

这一章是本版新增的核心。结论先行：快手实况的动效，不在网页 SSR 数据里。

4.1 六份实现的交叉验证

判断「能不能解析快手实况」，最硬的证据不是 README 宣传，而是代码里有没有真的填那个字段。

它把「实况」当成一等公民写进了数据模型，ImgInfo 专门留了 livePhotoUrl 字段， 文档还写着支持 Douyin「image albums and Live Photos」。但在 KuaiShou.php 里：

模型留好了、字段留好了，快手这条链路就是不填。只有一个解释：快手网页数据里没有这个东西可取。

4.2 一个不该被忽略的反证

你的实测记录里有一句关键观察：单张实况的 ext_params.single.volume = 1。

推理链
volume 是音轨／音量语义。一张静态 JPEG 不可能带音量。 所以「实况的动效+声音」在平台侧确实存在一条媒体流，只是没有出现在你能抓到的那份 JSON 里。
结论：不是"没有"，而是"不在这个数据源里"。这决定了补齐方向是换数据源，而不是换解析方式。

4.3 两种数据模型：先判定，再改代码

这是最容易返工的地方。同样是"实况"，三个平台的编码方式完全不同：

平台实况编码方式字段位置模型
抖音 每张图各配一段短 mp4 images[i].video.play_addr.url_list[0] 模型 B · 一图一段
微博 每张图各配一段 pics[i].videoSrc 模型 B · 一图一段
小红书 同名文件配对 imageList[i].stream（对象，键 EF4/EF5…）→ NN.jpg + NN.mp4 模型 B · 同名配对
快手 未知 atlas.list 只有静态图 待判定
两种可能的模型，改动量差一个数量级

模型 A · 整条一段：一个 mp4 + N 张图。此时 live 的语义是"整条的动效地址"， 每张图都指向同一个 URL。改动 3 行，但要改 UI 的播放逻辑（不然 N 张图会播同一段）。

模型 B · 一图一段：N 个 mp4，与 atlas.list 按下标对齐。 改动 3 行，UI 逻辑与抖音完全一致，可直接复用。

判定标准（写死，别靠"看起来成功"）

形态通过标准反向陷阱
单张实况1 图 + 1 mp4—
实况合集（N 张）N 图 + N 个 mp4 只有 1 个 mp4 而图有 N 张 → 是模型 A，不是一图一段。必须用 Σ时长 ≈ photo.duration 交叉验证， 别把整条视频塞给每张图
混排（图 + 视频）按 kind 分开，live 只挂 image—

4.4 为什么微信小程序"可以"

这是最容易被误导的一点。小程序能播快手实况，通常不是它更懂快手，而是：

  1. 后端接了商业 SaaS 解析——云析、极速通道这类都明确宣传覆盖"快手实况"，适配工作由服务商做了；
  2. 展示是伪实况——封面图 + 叠一个 <video> 播放，用户感知不出来；
  3. 下载靠域名白名单——小程序 downloadFile 要求合法域名，short_videos 仓库里就带了一份 343 个域名的 download_whitelist.txt。
所以"小程序能"≠"背后拿到了 Live Photo 的那对文件"
对你有两条启示：① 用户对"伪实况"的接受度很高，L1 方案（静态图 + 叠层播放）性价比极高； ② 如果确实要"真解析"，得往 App 接口方向走，不是抄小程序。

6.3 顺带值得抄的两个工程细节

① 文件类型嗅探代替扩展名猜测（来自 KS-Downloader）
快手 CDN 地址常无后缀或后缀与实际编码不符。用文件头 magic number 判类型（mp4/m4v/mkv/flv/webp/avif），比猜后缀可靠。

② 按平台给 Referer（你自己在微博上踩过的坑）
*.sinaimg.cn 防盗链只认平台自己的 Referer，带别人的会被拒。同一个道理适用于快手 CDN—— 下载与预览都要带上 https://www.kuaishou.com/。你的 DIRECT_URL_HOSTS 已经加了 ndcimgs.com / kwimgs.com，值得确认 Referer 也一起给了。

7十一个坑

全是从别人源码注释、你踩过的记录里捞出来的，比架构更值钱。

短链跳转次数不固定

v.kuaishou.com/{code} 可能 1–3 跳，且落点由 UA 决定：桌面 UA 落到 JS 壳页（零数据），移动 UA 才落到 SSR 页。你的代码已经处理了这条。

长视频路由结构不同

/fw/long-video/ 必须改写为 /fw/photo/，或单独走 manifestH265.json.adaptationSet[].representation[].backupUrl。

JSON 里嵌了非法片段

畸形字符串化数据、匿名函数、尾逗号。先 json.loads，失败再清洗或括号配对截取。

顶层 key 被位移混淆

tusjoh = string +1。别按 key 取，深度遍历找特征节点。

图集 CDN 域名会变

别硬编码 tx2.a.yximgs.com，从 atlas.cdn[0] / cdnList 动态取，硬编码只作最后兜底。

直链有防盗链

CDN 校验 Referer + UA，浏览器直接 <video src> 会 403。要服务端/本地代理并透传 Range。

直链有时效

别把直链当长期资产缓存。缓存「解析结果 + 短 TTL」，不缓存 URL 本身。

result 语义要分清

1 成功 / 2 风控（指数退避 5·2ⁿ）/ 50 缺签名。不区分会把"被限流"误判成"内容不存在"。

扩展名不可信

用 magic number 嗅探。你的图集下载产物是「真 JPEG（ff d8 ff e1 + Exif）」，这个校验方式是对的，可以推广到视频。

竖屏的 height 是长边

1080×1920 若按 height 当档位会显示成 1920p。你已修（优先读 qualityType），这是很多项目没做的细节。

并发与限速

成熟项目都有内置延时（KS-Downloader 抽了 tools/sleep.py），下载并发默认 4。别把解析做成无脑并发。

8合规边界

技术可行 ≠ 产品可做。这一节会直接影响你的功能取舍。

三条最硬的红线

① 去水印 / 绕过技术措施。快手作品直链本身多为作者上传的原始文件，所以"无水印"对快手而言常是自然结果而非破解。 但主动去除平台叠加标识、或破解付费/私密内容，在《著作权法》技术措施条款与《反不正当竞争法》下风险显著。

② 批量采集与再分发。单条链接的用户主动解析，与"按作者/关键词批量抓取并建库分发"，性质完全不同。后者需要明确授权基础。

③ 平台协议。未经许可的自动化访问通常违反用户协议，平台可封禁、限流、主张民事权利。这是商业风险，不是技术风险。

把它做成产品能力，而不是法务文书

  • 定位为「个人备份 / 已授权素材提取」，不做「全网采集库」。文案、功能、默认参数要一致。
  • 不做批量入口（主页批量、关键词搜索）——顺带绕开了 __NS_hxfalcon 这个最大技术债。
  • 私有内容一律明确不支持：私密作品、付费内容、需登录可见的，返回「不支持」而非「解析失败」。这既是合规也是产品诚实度。
  • 保留删除通道：权利人可申请移除；日志不长期留存作品元数据。
  • 署名与来源：解析结果尽量保留作者信息（你已有 uploader / uploader_id），便于用户溯源与合规使用。
  • 许可证：借鉴 GPL-3.0 项目（KS-Downloader）只取思路；要复用代码就选 Apache-2.0 / MIT 的。

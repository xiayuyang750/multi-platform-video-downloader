## 一、3.1 快手平台（已完成 2026-10-22）

### 原任务描述（原文照录）

> 尚未开始。需要先确认：分享链接形态、是否需要登录/签名、图文/视频分别走哪条链路。

### 实测结论

1. **必须用移动 UA**。分享短链 `v.kuaishou.com/<code>` 的落点由 UA 决定：
   桌面 UA → `www.kuaishou.com/short-video/<id>`（JS 壳，零数据）；
   移动 UA → `v.m.chenzhongtech.com/fw/photo/<id>`（服务端直出完整 JSON）。
2. **不需要登录、不需要 Cookie、不需要 `__NS_sig3` 签名**。纯 HTTP 即可，
   与开源同类工具（KS-Downloader）的做法一致。
3. 页面数据在一个 `<script>` 里，**根对象 key 被凯撒位移混淆**（`tusjoh` = `string`），
   内层字段名正常。因此解析按「值里同时含 `photoId` 与 `photoType`」定位，
   不能写死路径。

### 各形态与数据位置

| 形态 | `photoType` | 数据位置 | 产出 |
|---|---|---|---|
| 视频 / 橱窗视频 | `VIDEO` | `photo.manifest.adaptationSet` + `mainMvUrls` | 1080p / 720p 档位，实测 206 + `avc1` |
| 图集 | `HORIZONTAL_ATLAS` | `ext_params.atlas`（`list` + `size` + `cdnList`） | N 张静态 WebP 原图 |
| 长图图集 | `VERTICAL_ATLAS` | 同上 | 同上 |
| 单张图片 | `SINGLE_PICTURE` | `coverUrls[0]` | 1 张原图（尺寸与 photo 宽高一致） |
| 单张实况 | `SINGLE_PICTURE` + `ext_params.single.volume=1` | 同上 | **只有静态图** |
| 实况合集 / 混排 | `HORIZONTAL_ATLAS` | `atlas` | **只有静态图** |

### 已知限制：实况拿不到动效

网页数据里没有任何「每张图的动效地址」，下载到的 WebP 也没有 `ANIM` 块
（实测图集首图 17 KB、实况集首图 252 KB，两者 `ANIM=False`）。
动效应在 App 内部接口（带签名）里，本期不做。

处理方式：一律按「图文」入库，不假装是实况；单张实况额外标注
「该作品含动效，当前仅支持静态图」。

**2026-10-23 复核（纯 HTTP，五项全否）：**

| 探测 | 结果 |
|---|---|
| 分享页 SSR 搜 `.mp4` | 0 次，`photo.mainMvUrls` 为空数组 |
| 图集 `_0.webp` | 117 KB，无 `ANIM` / `VP8X` 块，是静态有损 WebP |
| 猜 CDN 路径 `_0.mp4` / `.mp4` / `_0.mp4_h264.mp4` | 全 404 |
| 页面预加载的真接口 `/rest/wd/ugH5App/photo/simple/info` | 直连返回 `result:21 参数格式错误` |
| App 级 `/rest/wd/photo/info` | `2001 antispam need captcha` |
| 旧域名 `m.gifshow.com/fw/photo/<id>` | 同样 `mp4hits=0` |

热门小程序「蝴蝶视频提取下载解析」「一键无损去水印」都能出实况 mp4，实测两者
给的是**同一套**链接：`v1-plat-fdl.ws**u**kwai.com/ksc2/<200 字符密文>.mp4?pkey=…`，
域名是对快手官方 CDN `ws**k**wai.com` 的一字之差仿冒；视频本身是 HEVC 720×1280
（快手自己的转码规格），`Server: tencent-cos`、`Content-Range` 正常返回，
但路径是不可推导的密文，且复制前强制看 30 秒广告。

结论：对方是「先用自己的通道拿 App 接口地址 → 落腾讯 COS → 重新签名分发」，
**URL 不可复用、算法不可推导**，不能作为本项目的接入方式。

### 实现位置

- `ytdlp_engine.py`：`_ks_fetch` / `_ks_ssr_json` / `_ks_find_photo` /
  `_ks_video_tiers` / `_ks_atlas_media` / `Engine._parse_kuaishou`
- `PLATFORM_RULES` 增加快手（`kuaishou.com` + `chenzhongtech.com`）
- `DIRECT_URL_HOSTS` 增加 `ndcimgs.com` / `kwimgs.com`
- 界面：快手品牌图标（simple-icons CC0）、品牌橙 `#FF4906`、
  解析提示「正在间接读取快手作品数据…」（区别于抖音的「直接读取」）

### 验收结果（13 条真机链接）

| 形态 | 结果 |
|---|---|
| 视频 / 橱窗视频 ×3 | 720p 播放、1080p 下载；下载产物 4.98 MB |
| 单张图片 | 1 张 |
| 图集 / 长图图集 ×3 | 9 / 25 / 7 张 |
| 单张实况 | 1 张 + 动效提示 |
| 实况合集 ×2 | 31 / 5 张 |
| 混排 ×2 / 混合合集 | 30 / 27 / 10 张 |

图集下载产物为真 JPEG（`ff d8 ff e1` + Exif），说明 WebP 转换链路正常。

### 踩过的两个坑（已修）

- **竖屏视频的 `height` 是长边**：1080×1920 会显示成「1920p」。改为优先读
  `qualityType`（平台自己的档位名），没有才退回短边。
- **同分辨率两条码率**：标签重复成两个「720p」。按档位名去重、保留高码率那条。

### 遗留

- **实况动效：已定性为「本期不做」**。H5/分享页不含动效源，App 接口带签名且需
  过 antispam；第三方（两个热门小程序）走的是「仿冒域名 + COS 中转 + 密文路径」，
  URL 不可复用。真要拿只有两条路：逆向 App 的 `__NS_sig3`（易失效、属对抗风控），
  或接付费第三方 API（成本 + 合规风险）。两条都暂不选。
- 封面单下、BGM 单下
- 官方图标用 simple-icons 的 Kuaishou 路径，与 Windows 端 `brand-icons.js` 已同步

**2026-10-23 真机验证（release APK，`10AF1M1Z030018H`）：**

- 解析主页平台行：YouTube / B站 / 抖音 / **快手** / TikTok / X / Instagram / 小红书 / 微博 / 公众号 ✓
- 用 ACTION_SEND 分享意图传入 `https://v.kuaishou.com/7DVRA1It`，自动解析成功：
  平台「快手」、标题「美女手机动态壁纸#气质美女 #动态壁纸 #live动图 #实况」、
  作者「飞车出库 · 2042997771」、形态「图文 · 共 5 张」✓
- 加载提示连测 3 次均为「正在间接读取快手作品数据…」✓

## 六、3.8 知乎平台解析（已调研，暂不做）

### 结论

2026-10-22 完成探针后决定**本期不做**。原因不是"做不到"，而是投入产出比不成立：
知乎网页本身就能保存图片、复制正文，我们唯一能补的缺口只有视频；
而视频只覆盖「想法 / zvideo」，用户贴得最多的「回答」需要登录态。

### 需求（原设想）

用户贴知乎链接时能解析并下载：回答里的图片、回答里的视频、专栏文章、知乎视频（zvideo）、想法（pin）。

### 链接形态

| 形态 | 典型地址 | 接口实测结果 |
|---|---|---|
| 想法（图文 / 视频） | `zhihu.com/pin/<id>` | **200，无需登录** |
| 回答 | `zhihu.com/question/<qid>/answer/<aid>` | **403 `need_login:true`** |
| 专栏文章 | `zhuanlan.zhihu.com/p/<id>` | 403（同上） |
| 视频 | `zhihu.com/zvideo/<id>`、`zhihu.com/video/<id>` | 走 `lens.zhihu.com`，200 |
| 外链跳转 | `link.zhihu.com/?target=...` | 跳板，不是内容 |

### 关键实测数据

1. **页面与 `api/v4` 一律 403**，返回 `zse-ck` 挑战页（带一段需要浏览器执行的 JS）。
2. **想法接口可用**：`GET /api/v4/pins/<pin_id>` → 200，
   `content[1].video_id` → `GET lens.zhihu.com/api/videos/<video_id>` → 200，
   playlist `hd 720x1280 / sd / ld`，`vdn6.vzuu.com` 直链实测 `206 + avc1`（H.264）。
3. **回答接口不可用**：`/api/v4/answers/<aid>` 返回
   `{"error":{"need_login":true,"code":40353,"message":"请您登录后查看更多专业优质内容。"}}`。
   用户在浏览器里关掉登录弹窗仍能看全文，是因为**页面本身**对浏览器开放，
   接口则绑定登录态。

### 若将来要做，路线已经清楚

- 想法 / 视频：纯 HTTP，链路已验证，接 `DIRECT_URL_HOSTS` 即可。
- 回答 / 专栏：必须 WebView + 登录态（识别 `zse-ck`、关弹窗、读 `js-initialData`）。

### 若启用时的验收标准

- 想法（图文 / 视频）各 1 条、zvideo 1 条解析成功；视频可播放可下载。
- 历史分组出现「知乎」，不再是「其他」。

### 当前表现

知乎链接未接入 `detect_platform`，会落到 yt-dlp 通用提取器并报
「被平台拒绝（403）」。**遗留问题**：这句提示会说「可能需要 Cookie」，
容易把人引到错误方向；下次动到这块时改成「知乎暂不支持」。

## 七、2026-10-22 ~ 10-23 的修复与体验调整

### 7.1 抖音个别视频解析失败（已修）

**现象**：`https://v.douyin.com/hxR0p932zd0/`（标题 `#djmico`）真机报
「15 秒内没能取到这条作品的数据」，但同类「抖音下载器」能正常解析。

**根因**：`aweme/v1/feed/` 不是按 id 精确查询，而是「以 aweme_id 为种子拉一条推荐流」——
平台愿意服务时种子排在第一条，不愿意服务时接口**照样返回 200、只回无关推荐**，
所以表现为「静默漏掉」，不是报错。愿不愿意服务由**渠道号 `aid`** 决定，
各渠道的作品池互不覆盖：

| 作品 id | `aid=1128`（抖音主站） | `aid=6383`（火山版） |
|---|---|---|
| 7696897222785752937（本缺陷） | 漏，返回 5 条无关 | **中，排第一** |
| 7692727357479989234（实况合集 2） | **中** | 漏 |
| 其余 7 条测试链接 | 中 | 中 |
| 7693090141682334373（实况合集 1） | 漏 | 漏 |

**修复**：新增 `DOUYIN_FEED_AIDS = ("1128", "6383")`，两个渠道**并发**请求、命中即用；
`aid` 从 `DOUYIN_COMMON_PARAMS` 移到 URL 模板。两者都漏时仍走原有 WebView 兜底。
不能只留 6383 —— 上表第二行就是反例。

**水印核对**：`aid=6383` 返回的 `play_addr` / `download_addr` 的 `uri` 与 1128 完全一致
（`v0200fg10000db8du3nog65nj210o7hg`），URL 中无 `water` 字样，换渠道不引入水印。

**验证**：真机解析成功（抖音 / `#djmico` / `🌈_  DJ女神ོ` / 0:08 / H.264 / 3.5 MB）。
回归 4 条：`mJsVdcGbhIo`、`D_Mx3se-kmk`、`w0qCK-A8qCY` 正常；
`CJhaXy9LB8U` 仍失败，但**改动前同样失败**（两个 aid 都漏），不是本次引入。

**遗留 → 2026-10-23 已补强（见 7.3）**：

- 同 id 重试：**最终没做**。评估后放弃 —— 没有任何证据表明它能提高命中率，
  却让「笔记」这类必然落空的场景多跑一轮（实测 4 次请求 + 0.4 秒休眠，已回退）。
  改为两个 aid 并发，把耗时压回 1 个往返（见下条）。
- WebView 兜底的数据获取：已改为「页面自己的 fetch/XHR 钩子优先，原生重放兜底」。
- `CJhaXy9LB8U` 另有结论：**作品已被抖音删除**，不是解析缺陷（见 D2）。

### 7.2 体验调整

| 项 | 改动 | 原因 |
|---|---|---|
| 标题 | 压成一行；超 **50 字**截断补「…」 | 极个别作品标题极长，撑坏列表与详情页 |
| 正文 | 上限 4000 → **20000** 字 | 长文案被腰斩 |
| 正文去重 | 正文与标题相同则置空；纯符号置空 | 避免详情页标题下面重复一遍 |
| 解析提示 | 按链路区分：抖音「正在直接读取抖音作品数据…」、快手「正在间接读取快手作品数据…」、X「正在通过第三方解析服务…」、小红书 / 微博「正在打开内置浏览器…」、视频号「正在读取视频号公开信息…」、其余「正在使用内置解析引擎…」 | 原来的统一文案说不清「慢在哪、走没走内嵌浏览器」 |
| VPN 提示 | 仅当提示含「引擎」或「第三方」时显示横幅 | 内置浏览器走系统网络，提示 VPN 会误导 |
| 平台列表 | 补上**快手**、**公众号** | 解析能力早就有了，主页没列 |
| 品牌图标 | 快手用 simple-icons 官方路径（CC0），橙色 `#FF4906`，Android 与 Windows 端 `brand-icons.js` 同步 | 与其它平台一致 |
| 画质标签 | 抖音补 `play_addr.data_size` 作为体积；「平台默认档」标注移到体积之前；体积统一放最后一列 | 默认档缺体积、三列顺序乱 |
| 抖音实况判定 | 「任意一张带动效」→ **「每一张都带动效」**才判实况 | `一大波照片释出`（26 张、`live_photo_type=0`、仅 1 张带 `playAddr`）被误判成实况 |

### 7.3 抖音 WebView 兜底改造（2026-10-23）

兜底链路原来只有「原生 HTTP 重放」一条取数据的路，而重放带着「不是页面自己发的」
痕迹，抖音经常回 `HTTP 200 + 空响应体`。现改为三级：

| 优先级 | 路径 | 做法 | 状态 |
|---|---|---|---|
| ① | **页面钩子** | 注入 JS 包住 `fetch` / `XMLHttpRequest`，详情接口的响应体经 JS bridge 回传原生 | 新增，已生效 |
| ② | 原生重放 | `shouldInterceptRequest` 拿到请求后自己再发一次 | 保留为兜底 |
| ③ | 主文档 | 图文 / 图集 / 实况图的 SSR 数据 | 不变 |

关键实现点：

- **不需要额外 Cookie / 登录**：钩子是旁听页面自己发出的请求，页面带什么就用什么。
- `XMLHttpRequest` 与 `fetch` 都要包（页面两条路都在用）；`fetch` 必须 `clone()`
  再读，否则会把响应体吃掉导致页面白屏。
- 钩子只回传「URL 含 `aweme/detail` 或响应体含 `aweme_detail`」的响应，其余静默丢弃；
  日志也只记 `/aweme/` 路径下的请求。
- **作品编号双保险**：优先用页面地址里的编号，地址还没跳转完时退回从请求 URL 的
  `aweme_id=` 取；两者都拿不到就丢弃，绝不盲收推荐位里别人的作品。
- JS 侧用 `window.__ytHook` 做幂等，`onPageStarted` 与 `onPageFinished` 各注入一次。

**验证**：真机日志确认钩子装上并持续拦截页面请求（`hook seen: .../aweme/v1/web/aweme/detail/...`）；
回归 4 条（`hxR0p932zd0`、`D_Mx3se-kmk`、`mJsVdcGbhIo`、`CJhaXy9LB8U`）无新增失败。

**注意**：钩子只在「页面真的去请求详情接口」时才有用。若页面不走该接口
（例如作品不存在、被重定向到推荐流），钩子没有目标可拦 —— 这属于数据源问题，不是钩子的缺陷。

**2026-10-23 补测：钩子能否让「视频」走 WebView？结论是否。**

做法：临时把 `DOUYIN_FEED_AIDS` 置空，强制视频走 WebView，用 `hxR0p932zd0`（公开视频）实测。
结果：

| 观测 | 结果 |
|---|---|
| 主文档 | 72914 / 816111 字节，`images=false`、`playAddr=false` |
| 钩子是否拦到详情请求 | **是**，`aweme/v1/web/aweme/detail/` 出现 5 次 |
| 页面自己拿到的响应体 | **`len=0`**（`hook detail: len=0`） |
| 原生重放 | 同样 `len=0` |

说明：钩子本身完全正常（它读到的就是页面自己那份响应），
但抖音对无头 WebView 的详情接口**连页面自己发也回空响应体**。
所以 WebView 这条路对视频类作品依然不可用，视频只能靠 aid 接口拿。
这也解释了本次 bug 修复前的现象：作品公开可见，却两条路都拿不到。

### 7.4 解析耗时的取舍

**2026-10-23 真机实测（5 条抖音链接，分段计时）：**

| 阶段 | 耗时 | 占比 |
|---|---|---|
| ① 短链展开（`v.douyin.com` → 真实 id） | 680~930 ms | 约 25% |
| ② 查作品数据（两个 aid 并发） | 1500~2100 ms | 约 70% |
| ③ 本地入库 / 整理档位 | < 20 ms | — |
| **总计** | **2.2~3.1 s** | |

**发现并修掉的缺陷**：并发之后写成了 `for w: w.join()`，那是等**最慢**的那个，
而两个 aid 的响应速度差 0.5~1.5 秒。改为「谁先命中就先返回」。实测收益：

| 链接 | 改前 | 改后 |
|---|---|---|
| `hxR0p932zd0` | 2904 ms | **2246 ms** |
| `D_Mx3se-kmk` | 2733 ms | **2582 ms** |
| `mJsVdcGbhIo` | 3655 ms | **3058 ms** |

顺带修掉一个隐患：原来 `join(timeout=25)` 是两个线程各等 25 秒，最坏 50 秒；
现在是一个整体 25 秒的截止时间。

**代价说明**：抖音现在每次并发问两个 aid。多出来的那个请求**不增加等待时间**
（并发），只在极少数「两个都落空」的情况下才需要等齐。

**第二处优化：短链只读第一跳。** 实测第一跳的 `Location` 里就已经带着作品编号
（`https://www.iesdouyin.com/share/video/<id>/...`），而 `urllib` 会继续跟随到
iesdouyin 甚至 douyin.com 并下载整个分享页 —— 多出来的 1~2 个 TLS 往返纯属浪费。
改为用 `http.client` 只发一次请求读 `Location`，拿不到编号再退回自动跟随（保底不丢功能）。

| 阶段 | 优化前 | 优化后 |
|---|---|---|
| 短链展开 | 680~930 ms | **355~415 ms** |
| 端到端（视频） | 2.9~3.0 s | **2.1~2.3 s** |

**还没做的**（按性价比）：

| 方案 | 预期收益 | 说明 |
|---|---|---|
| 结果缓存（同链接短时复用） | 重复解析省 2~3 s | 首次无收益；需定过期策略 |
| 连接预热（启动时预建 TLS） | 首次省 200~400 ms | 复杂度中等，收益有限 |

剩余的最大头是「查作品数据」那 1.5~1.9 秒，属于抖音服务端响应时间，客户端没有优化空间。

**已放弃的方案**：「串行 + 整轮重试 1 次」。笔记类要发 4 次请求再加 0.4 秒休眠才降级，
实测明显变慢，已回退。

### 7.5 失败要快、要准：各平台的失败策略

原则：**能判断就立刻给结论，判不出来才等超时；提示只写已确证的原因，不罗列可能性。**

| 平台 | 取数路径 | 失败判据 | 失败耗时 |
|---|---|---|---|
| 抖音 | 接口（aid 并发）→ WebView | ① 出现 `web_video_404_link` → 已删除/私密<br>② 页面加载完成后详情接口**连续 2 次**回空 → 限流/未开放<br>③ 页面加载完成但从未请求详情 → 疑似改版<br>④ 页面没加载完 → 网络问题 | ①立即 ②约 4~5 s ③④**12 s** 兜底 |
| 快手 | 纯 HTTP 移动页 | 请求异常 / 页面无 `photoType` | 1~2 s（天然快） |
| 小红书 | WebView | 8 次重试（固定 800 ms）仍无数据且**不需要登录** → 已删除/私密 | 约 **6.4 s**（原 16.8 s） |
| 微博 | WebView | 8 次重试（固定 700 ms）用尽；文章页与正文页文案分开 | 约 **5.6 s**（原被 15 s 超时截断） |
| yt-dlp 平台 | yt-dlp（B站/YouTube/TikTok/X/IG/公众号） | 引擎错误映射（`friendly_error`） | 正常几秒；最坏约 20 s，外层上限 **30 s** |

2026-10-23 本轮改动：

- 抖音：空详情 ×2 即报；兜底超时 15 s → **12 s**。`MBgDyOExZ4w` 实测 6 秒内出结论。
- 小红书：重试间隔由 `800ms × n`（累计 16.8 s）改为固定 800 ms × 8 次（6.4 s），用尽即报。
- 微博：重试间隔由 `700ms × n`（理论 25.2 s，**比 15 s 超时还长，导致「重试用尽」分支永远走不到**）
  改为固定 700 ms × 8 次（5.6 s）。
- yt-dlp：`extractor_retries` 由默认 3 改为 **1**（默认值配 20 s socket 超时最坏能拖 60 s+）；
  `socket_timeout` 20 s → **10 s**（单次网络操作，不影响正常解析）；
  外层解析上限 75 s → **30 s**，Windows 端 `PARSE_TIMEOUT` 同步改 30。
  没压到 12 s 的原因：YouTube 要解 JS 挑战（n-sig），正常也要 8~15 s，压太短会误判。

## 八、缺陷清单

### D1 抖音视频偶发「画面缩左上角」

- 现象：播放时画面只占左上角一小块，其余区域黑屏。
- 现状：v1.0.6 未复现，无稳定样本。
- 下一步：收集 3 条可复现链接 + 机型/系统版本；先看 `VideoPlayer` 的 `aspectRatio` 与 `resizeMode` 分支，再看是否与 H.265/异常宽高 metadata 有关。
- 不在 3.4 范围内，不与正文改动混在一起修。

### D2 抖音实况合集 `CJhaXy9LB8U` 解析失败（已定位：作品已被删除）

- 现象：`https://v.douyin.com/CJhaXy9LB8U/`（`7693090141682334373`）报「15 秒内没能取到这条作品的数据」。
- 已排除 aid 渠道：`aid=1128` 与 `aid=6383` 都只回该 id 之外的推荐流（各 6 条）。
- **根因（2026-10-23 定位）**：这条作品在抖音上已不存在。平台不是回错误页，而是把请求
  重定向到精选推荐流，地址带标记：
  `https://www.douyin.com/jingxuan?previous_page=web_video_404_link&modal_id=...`
  因此详情接口对页面自己也回空响应体（`detail via replay: len=0`），主文档也没有作品数据
  （819 KB 但 `images=false`、`playAddr=false`）。之前听到的音频，是重定向后推荐流在自动播放。
- **处理**：`onPageStarted` 检测到 `web_video_404_link` 立即结束并给出文案
  「这条作品已被作者删除，或已设为私密作品。」，不再空等 15 秒。
- 结论：这不是解析缺陷，无法通过换链路修复。

### D3 抖音「被限流」作品：作品存在但公开接口不服务（已知限制）

- 样本：`https://v.douyin.com/MBgDyOExZ4w/` → `7698637427908798329`（标题含「黑丝」等敏感词）。
- **作品存在**：长链 `www.douyin.com/video/<id>` 直接 200，**没有**跳 `web_video_404_link`。
- **公开接口全渠道不服务**：实测 `1128 / 6383 / 2329 / 3004 / 3711 / 2702 / 2010 / 2901 / 7497`
  共 9 个渠道号，返回的都是无关推荐流，无一命中目标。
- WebView 也救不了：视频页的详情接口对无头 WebView 回空响应体（见 7.3 实测）。
- 结论：这是平台分发策略造成的能力边界 —— `aweme/v1/feed` 本质是推荐流，不是查询接口，
  平台不放进池子的作品，客户端没有任何合法手段取到。**无法修复，只能如实提示。**
- 对用户的影响与文案：超时不再罗列"可能原因"，改为**按判据给结论**（`timeoutReason()`）：

  | 判据 | 得出结论 |
  |---|---|
  | 页面出现 `web_video_404_link` | 这条作品已被作者删除，或已设为私密作品。 |
  | 页面加载完成 + 详情接口回空响应体 | 抖音没有开放这条作品的公开数据（这类作品通常处于限流状态），只能在抖音 App 内观看。 |
  | 页面加载完成 + 详情接口一次没被请求 | 可能是抖音改版，欢迎用「意见反馈」告诉我们。 |
  | 页面没加载完成 | 页面没能加载完成，请检查网络后重试。 |

  判据来自真实观测（`pageLoaded` / `emptyDetail` 两个标记），不是穷举可能性。
  真机验证：`MBgDyOExZ4w` 给出限流结论，`CJhaXy9LB8U` 给出删除结论，正常视频不受影响。

**同类软件为什么"能解析"**：实测另一款抖音下载器在这条链接上返回的是**别的视频** ——
它把推荐流的 `aweme_list[0]` 当成结果交了出去（伪成功）。本项目明确禁止这种回退
（见 `_parse_douyin_via_api` 注释：宁可失败，也不把别人的作品当结果），所以会如实报错。
